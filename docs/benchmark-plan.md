# Research Loop 的 MLE bench 验证计划

状态：新框架已实现，Aerial Cactus 单轮真实接线已完成；三任务 27-run 对照尚未执行。日期：2026-11-01。实测结果与限制见 [v2 验证记录](verification-v2.md)。

## 基准与首批任务

主基准采用 MLE-bench，开发阶段先运行其 Lite 清单中的三个任务。MLE-bench 包含 75 个 Kaggle 来源任务，覆盖数据处理、模型训练和实验优化；Lite 是其中 22 个低复杂度任务。基准提供离线数据准备与评分代码，可将任务和评分器接入现有 Codex/Pi 控制器，不需要采用 AIDE 的搜索实现。[官方仓库](https://github.com/openai/mle-bench)、[论文](https://arxiv.org/abs/2410.07095)、[Lite 任务清单](https://github.com/openai/mle-bench/blob/main/experiments/splits/low.txt)

| 任务 ID | 任务及官方主指标 | 本次验证用途 |
| --- | --- | --- |
| `aerial-cactus-identification` | 32×32 图像二分类；ROC-AUC 越高越好 | 首个真实训练闭环，观察结构、增强和训练配置的探索 |
| `denoising-dirty-documents` | 文档图像去噪；像素 RMSE 越低越好 | 比较不同方法路线，检查局部误差与最终图像质量之间的关系 |
| `spooky-author-identification` | 三类文本作者识别；多分类 log loss 越低越好 | 检查神经网络以外的特征、模型和概率校准路线 |

任务和指标依据：[Cactus 描述](https://github.com/openai/mle-bench/blob/main/mlebench/competitions/aerial-cactus-identification/description.md)、[Denoising 描述](https://github.com/openai/mle-bench/blob/main/mlebench/competitions/denoising-dirty-documents/description.md)、[Spooky 描述](https://github.com/openai/mle-bench/blob/main/mlebench/competitions/spooky-author-identification/description.md)。表中的验证用途为本项目的实验设计，路线由 Agent 提出，不预先分配某条路线为获胜方案。

三任务结果只称为开发子集结果。正式评估再扩展到事先固定的 Lite 任务集合，完整 Lite 才按其官方聚合协议报告成绩。开发使用过的任务须单独标记，新增任务用于检查策略调整后的迁移表现。

## 可用资源

远程执行前由操作者确认 GPU、内存和磁盘可用性，显式指定 SSH 主机、任务目录与空闲 GPU。此设计不预留资源。

官方列出的 Lite 数据总量约 158GB，尚不包括本项目额外的工作区与训练产物。首轮按任务下载，并先确认处理后数据、依赖和 checkpoint 的存放空间，不执行全量准备。数据获取需要 Kaggle 下载权限，部分任务可能还需要账户接受相应规则。[官方数据准备说明](https://github.com/openai/mle-bench#dataset)

每个 run 使用相同的 CPU、内存和最多一张 GPU 配额；多卡用于不同 run 并行。选择已确认空闲的卡，不停止已有任务。各组具有相同模型资产、网络权限和依赖条件，准备完成后使用隔离的工作目录和可确定的产物版本。

## 对照组

| 组 | 方法 | 比较目的 |
| --- | --- | --- |
| A | 同一个 Codex/Pi Agent 自主多次训练和改进，保存结果 | 测量普通 Agent 迭代的表现，不使用一次性回答作为弱基线 |
| B | 当前线性 Plan → Execute → Review，使用共享研究文档 | 测量现有研究循环的表现 |
| C | 新设计的 Route Selection、实验 DAG、双层 Frontier 与研究记忆 | 测量整套新设计相对 A、B 的增益 |

三组使用相同后端、准确模型请求、推理设置、工具、数据划分、评价器、初始工作区和资源配额。B 不人为删除历史证据；C 的 Advocate、Judge、Plan、Execute 和 Review 调用全部计入预算。选择的收益必须抵消其占用的时间与调用开销。

初始比较估计整套设计的效果，不能将 C 的改善归因于辩论、Frontier 或上下文中的某一个组件。若整套设计有稳定收益，再单独比较 C 与“相同研究图和记忆、用单个选择 Agent 代替辩论”的变体。

## 数据与评价合同

运行前固定 MLE-bench commit、任务清单、准备配置、模型请求、工具权限和预算。整个比较批次开始前冻结各组框架实现与初始提示词，后续策略修改归入新批次；run 内按协议生成和修改候选仍然允许。采用官方准备脚本生成的 public/private 划分；另在 public 的有标签训练数据内预先固定训练与开发验证划分，三组保持一致。

- Agent 只读取供拟合的训练视图和无标签开发输入；开发标签由独立评价器保管并返回开发成绩。原始带标签 public 全集与准备目录对 Agent 不可读，避免从中重建开发标签。
- 官方 private 标签与最终评分器放在研究 Agent 无法读取的独立权限环境，只在 run 结束后评分。
- 最终评分前，run 必须依据开发验证结果冻结一个最终提交，不允许看完 private 分数后换候选。
- 整批 run 的提交全部冻结后统一进行 private 评分；成绩不能通过全局文档、Frontier、Judge 或人为调整反馈给同批任何运行。
- Agent 不得修改固定划分与权威评价器，也不得查阅竞赛现成解法。技术文档访问和预训练资产权限在各组一致。

MLE-bench 本身是离线评估，提交为预测 CSV，提交格式检查与最终成绩不同；其 test 通常由原公开训练数据重新划分，而非 Kaggle 原始隐藏测试标签。[官方环境说明](https://github.com/openai/mle-bench/blob/main/environment/instructions.txt)

旧竞赛可能已有模型预训练污染；同模型配对比较能减少此差异，但不能消除污染，也不能将本次分数视为全新科学发现能力。

## 与 Frontier 和研究记忆的关系

每个任务、组别和重复分别建立独立 Study、记忆、Frontier 和工作区，不继承其他 run 的研究发现或候选。官方任务指标为主指标。初轮使用单一全局目标和资源约束，不新增混合总分。开发验证和最终验收属于不同评价范围：循环内的 Global Frontier 只使用允许反馈的开发验证结果；private 评分只用于最终报告。

Agent 可以为各路线定义参数量、训练成本、分组误差、收敛曲线或校准等局部量，区分优化维度和诊断观察。Local Frontier 的定义与条件不改变官方主指标；局部改善与全局改善分别记录。各候选必须绑定准确代码、配置、checkpoint 和评价记录。

多目标 Frontier 的集合计算、缺失维度处理、纠正后的重建和恢复正确性，通过小型确定性协议检查验证。主指标任务的最终成绩本身不能证明这些实现正确。若增加任务质量与成本的多目标 Study，须单列为本项目扩展实验，不混报为官方成绩。

## 执行阶段与预算

以下为建议预算，不是实测耗时或已获准启动的训练任务。

1. **真实路径 smoke**：在 Cactus 上完成新框架的路线选择、Plan、真实训练、开发验证、Review、版本与文档发布，以及冻结后的最终离线评分。核查评分器与 Agent 权限隔离，并保留失败记录。此阶段只验证真实路径，不比较研究收益；已完成一次成功闭环。
2. **三任务配对比较**：实现新机制后，三组各在三个任务上独立重复三次，共 27 个 run。建议每 run 最多 4 小时，采用相同硬件配额，并保留各阶段耗时。重复之间使用同一数据划分和配对训练种子表；API 推理随机性不假定完全可锁定。按任务与重复组成 A/B/C 区组，随机轮换执行顺序与 GPU 卡位，记录共享服务器的明显争用。
3. **扩大评估**：依据预先规定的扩大条件，在新增任务和更长预算上复验；冻结策略后再运行完整 Lite。调整后不反复用最终测试结果选择设计。

主比较采用相同墙钟与硬件预算。若能够可靠统计实际模型推理的 token 用量，批次开始前再固定统一总 token 上限，各角色全部计入；不能以外层 CLI 启动次数代替模型推理次数或 token。若无法获得可靠用量，只报告时间和硬件预算匹配，将模型用量标为未测，不声称模型计算预算也相同。

27 个 run × 4 小时，对 GPU run 预留单卡的统一配置，名义上限约为 108 个 GPU 配额小时，包含 Agent 思考和等待，并非实际 GPU 忙碌时间；文本任务若不需要 GPU，仍单独报告 CPU 与时间消耗。并行可以缩短日历时间，但不能减少总任务预算。数据准备、依赖安装和最终评分的时间另行报告。

缩短预算或使用不同硬件时属于本项目的受控比较，不直接与官方默认运行成绩等同。正式 Lite 的运行预算、重复方式与聚合方法遵循所固定版本的官方协议。[官方 benchmarking 说明](https://github.com/openai/mle-bench#benchmarking)

## 结果与判定

主要结果为 run 结束时冻结候选的 private 指标。每个任务分别报告三组的原始成绩、相对相同起点的提升、配对差值和胜平负；平局容差在看最终成绩前规定。不同任务的 AUC、RMSE、log loss 不直接平均。三次重复与三个开发任务只能提供初步证据，不能据此宣称通用优势。

同时报告：

- 有效提交率、失败及中断数量，失败 run 不从统计中删除。
- 墙钟时间、模型调用与实际可获得的 token 用量、GPU 配额与忙碌程度。
- 达到预定开发验证水平的耗时；分阶段列出选择、规划、执行和评审开销。
- 数据初始化时间、首个训练 batch 延迟、稳态吞吐和峰值显存；未测到的项标明未测，不额外加入昂贵扫描。
- 路线曝光与实际执行分布、候选版本和关键结论到证据的可追溯性；这些是过程诊断，不替代最终成绩。

C 在开发验证上改善但 private 上没有改善，不能认定研究收益成立；只增加路线、文档或实验次数也不能认定成功。如果 C 在同预算下重复获得更好的最终结果或更低的达标成本，才构成继续扩大测试的依据。若收益不稳定或选择成本过高，保留负结果并检查具体组件。

真实训练闭环、协议检查和同预算对照分别检验能否运行、实现是否遵守合同、研究策略是否有收益。MLE-bench 只提供机器学习工程任务上的证据，不能替代诊断、文献调查或理论推导任务的验证。
