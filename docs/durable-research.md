# Durable research operating contract

The [runtime entry point](../runtime/README.md) uses PiDurable 1.5 and official pi-env 1.5. Source retirement does not establish a production cutover; see [retirement](runtime-retirement.md). Native isolation requires macOS `sandbox-exec`; use Node.js >= 22.19, Python, uv and the root npm lockfile. Local macOS arm64 CPU and the fixed-program [AutoDL Cactus path](autodl-cactus-evidence.md) have separate measured evidence.

## Research and evidence

Each bounded round plans a change, executes one pre-authorized operation through its frozen backend and receives an independent fresh Review. Review sees the accepted Plan, public Execute summary, trusted receipts, actual candidate snapshots and raw results, plus referenced prior reviewed records. It distinguishes execution completion, validity, knowledge change, goal achievement and continuation. Receipts and immutable Review records are authoritative; Markdown knowledge is an aid to understanding, not measurement authority. An invalid receipt cannot establish goal achievement. `minimumRounds` is the human-required minimum before declaring the goal achieved, distinct from `maxRounds`, the authorized limit. A Review may stop earlier; reaching the limit alone is not goal achievement.

Only development feedback is admitted to this learning loop; final-only inputs or evaluation are rejected at initialization. The [synthetic CPU fixture](../benchmarks/cpu_regression/README.md) freezes candidate code and inputs, executes prediction in isolation, seals prediction bytes and candidate identity on the host, and runs a trusted scorer separately without importing candidate code. Private labels, preparation seed, evaluator and model authentication are not exposed to the candidate. Evaluation v2 compares MSE and MAE with the frozen training-target mean baseline on the same development labels; R² uses the development-label mean in its denominator. Development feedback and two rounds do not establish generalization or a research benefit.

The official Rust daemon runs with a clean `env -i` environment under Seatbelt, providing an OS boundary for the role's tools. Access is limited to the role's allowed paths. Do not treat model instructions as the isolation boundary.

The built-in backend runs local CPU prediction and trusted scoring. A fixed task entry may inject an `ExperimentBackend` with `run` and `readReceipts`; `StudyConfig.execution` freezes its ID, version and identity. Writable opening requires the matching adapter before model or database admission, with no fallback to CPU or dynamic application loading. Its receipts retain the real platform job identity. Prediction/scoring command arrays describe the built-in path; an injected adapter may leave them empty. The [Cactus adapter](../integrations/cactus_remote/README.md) keeps Pi and role tools on the local host and submits only typed parameters to a fixed trusted AutoDL trainer.

A durable serial background Manager processes reviewed records. Its tool freezes a restricted draft; the Manager publishes that content with a task-ID-based atomic replacement and records the publication. A failure before replacement retains the prior file, Review and pending records for recovery; replacement precedes the framework publication commit, so inspect state after interruption at that boundary. Round two can reference round one's Review without waiting for notes. A fresh read sees newly published notes without a separate snapshot call.

## Recovery and authorization

Authorization fixes the original absolute `expiresAt`, slots and per-job time limit. Neither recovery nor a new framework task refreshes them. Model use is bounded by that deadline and framework usage/cancellation; there is no separate provider-enforced budget ledger or implicit model-call limit. STOP or expiry forbids new admission and model work; status and reconciliation of existing effects remain available. Workflow cancellation does not imply cancellation of a physical job, which remains bounded by its original job deadline.

If acknowledgement is unknown, never resend the slot, including from a new task. Query the configured backend's submission entry to find the original job identity; the built-in CPU entry is `submission ROOT SLOT`. A PID's existence alone does not establish current process identity or liveness. Bind only the original job ID; binding verifies it against the original intent and collects when possible. Collect reports the last confirmed start or unknown state if no terminal result is available. Once the original result is collected, `resume` can continue a terminal unsuccessful framework task from its saved experiment to fresh Review without rerunning Execute, provided admission is still authorized. A saved Review is resumed from the record instead. `maintain` retries pending Manager publication under the same admission boundary. See the [CPU CLI examples](../runtime/README.md) or [Cactus remote submission commands](../integrations/cactus_remote/README.md).
